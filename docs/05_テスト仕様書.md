## 1. テストの方針

### 1.1 3つのレベル

| レベル | 確かめること | 方法 | AIの呼び出し | 費用 |
|---|---|---|---|---|
| 単体テスト | 部品ごとの動き（入力チェック、ヒアリングの進行、AI出力のチェック、利用制限など） | pytest | 偽物（FakeClient・FakeSDK） | 0円 |
| 結合テスト | 画面の操作の流れ（トップ → 業務情報 → ヒアリング → 資料の添付 → 診断結果） | Streamlit の画面テスト機能（AppTest） | デモ用の固定データ | 0円 |
| AI品質評価 | 本物のAIの質問・分析・提案の質 | 確認用スクリプト（scripts/run_scenario.py） | **本物**（Claude API） | 1回 約30円 |

### 1.2 本物のAIを単体テストで使わない理由

- **費用：** テストは修正のたびに何十回も実行するため、本物を使うと料金がかさむ
- **再現性：** AIの回答は毎回少しずつ変わり、失敗したときに「プログラムの不具合」か「AIの揺らぎ」かを区別できない
- **異常系：** 通信エラーや利用制限などは、本物では狙って起こせない。偽物ならわざと発生させられる

AIの回答の質は単体テストでは確かめられないため、AI品質評価として分け、**実行のたびに開発者の了承を得て**行う。

### 1.3 テスト自体の確認

テストが成功しても、「テストが誤りを見つけられるか」は分からない。重要な仕組みについては、**わざと不具合を入れてテストが失敗することを確かめ**、元に戻す（手作業での確認。結果は 06 に記録）。

## 5. 異常系のテスト（指示書の必須項目）

| 異常 | 期待する動作 | テストファイル |
|---|---|---|
| 必須項目が未入力 | 項目ごとにエラーを表示し、次へ進まない。入力済みの値は消さない | test_validation.py、test_app.py |
| APIキーが未設定 | AI診断を選べず、デモモードを案内する | test_guard.py、test_app.py |
| API通信エラー・時間切れ | 「接続を確認して再試行」と表示し、それまでの質問と回答は消さない | test_ai_client.py、test_hearing.py |
| API利用制限（429）・障害（5xx） | 「混み合っています。再試行」と表示（SDKが自動で2回再試行した後） | test_ai_client.py |
| APIキーが無効 | 再試行ボタンを出さず、管理者への連絡を案内する | test_ai_client.py |
| AIから想定外の形式・内容 | 1回だけ呼び直し、だめならエラー表示。出力上限で途中で切れた場合・回答拒否も種類を分けて扱う | test_ai_client.py |
| ユーザーの途中終了 | 「ここまでで診断」で不足項目を明示して結果を出す。「中止」で内容を消してトップへ | test_app.py |

## 6. AI品質評価

### 6.1 シナリオ

デモ用の架空シナリオ3本を共用する（要件定義 A6）。業務情報・添付資料はシナリオのものを使う。

| ID | シナリオ | 特徴 |
|---|---|---|
| sales_report | 月次売上集計（営業管理部） | Excel集計・転記・属人化。添付：集計差異の記録.csv |
| repair_reception | 修理依頼の受付・手配（お客様相談室） | お客様対応・状況共有。あいまいな回答あり。添付：お客様の声_抜粋.txt |
| travel_expense | 交通費の精算・承認（総務部） | 申請・承認。クラウド禁止の制約。添付：差し戻し記録_9月.xlsx |

### 6.2 実施方法

- 確認用スクリプトでシナリオを最後まで実行する
- 利用者の回答は、**AIが質問した診断項目に対応する**シナリオの回答を返す（模擬の回答者）。本物のAIはデモと違う順番で質問するため、回の順番ではなく項目で選ぶ。シナリオに回答のない項目には「すみません、その点は分かりません。」と答える
- 質問・回答・分析・提案・トークン数・費用を eval_results/ にJSONで保存する
- 利用状況は本番用とは別のファイルに記録し、1日の回数制限に数えない

### 6.3 評価の観点と合格基準（指示書9章の5観点）

| 観点 | 合格基準 |
|---|---|
| ① 適切な質問が行われるか | 1回に1つの質問。回答済み・「分からない」と答えた項目を聞き続けない（同じ項目は2回まで）。エラーで止まらない |
| ② 課題を正しく抽出できるか | 利用者が述べた問題（業務情報・回答・添付資料）が課題になっている。最も重要な課題がサマリーで示される |
| ③ 根拠のない推測を事実として扱わないか | 「事実」の課題の引用がすべて入力に実在する（格下げ0件、または格下げされて「要確認」で表示される） |
| ④ 改善案が現実的か | 業務に固有の内容で、制約（予算・使えるツール）を守り、最初の一歩が具体的 |
| ⑤ 不必要なシステム導入を推奨していないか | 新規システム導入は、より簡単な案の後に理由つきでのみ提案される |

### 6.4 費用の管理

1回の実行は約30円（実測）。実行のたびに開発者の了承を得る。API提供元の前払い残高（自動チャージなし）が確実な上限となる。

## 7. 手作業での確認

| 確認すること | 方法 |
|---|---|
| 画面の見た目 | 開発者がブラウザで確認し、気になる点を画面の画像で指摘する |
| AIモードでの操作 | 開発者が自身でAI診断を操作し、利用者としての感想を出す |
| ファイルを選んで添付する操作 | AIモードで samples/ のファイルを選んで確認する（ファイル選択の部品は画面テスト機能で操作できないため） |
