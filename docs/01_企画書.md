## 1. 企画の背景

### 1.1 業務改善の現場で起きていること

中小企業や大企業の現場部門では、次のような「改善したいが、何から手を付ければよいかわからない」状態がよく見られる。

- Excelでの集計、システム間の手作業による転記、紙やメールでの申請・承認が残っている
- 担当者は「面倒」「時間がかかる」と感じているが、**どこが本当の問題で、何が原因なのかを言語化できていない**
- 情報システム部門やITコンサルタントに相談しても、最初のヒアリングに時間がかかり、**相談の入口で止まる**
- 改善策として、いきなり新しいシステムの導入が検討され、**業務ルールの見直しや既存ツールの活用で済む課題にも費用がかかる**

### 1.2 課題の整理

| # | 課題 | 誰が困るか |
|---|---|---|
| C1 | 現場担当者が業務の問題点を構造的に説明できない | 現場担当者、情報システム部門 |
| C2 | 初回ヒアリングの質が担当者のスキルに依存する（属人化） | 情報システム部門、ITコンサルタント |
| C3 | 事実と推測が混ざったまま改善策が議論される | 管理職、意思決定者 |
| C4 | 改善策が「システム導入ありき」になりやすい | 経営層、予算管理者 |

※ 上記は一般的な業務改善の現場を想定した課題であり、特定企業での調査・実測に基づくものではない。

## 2. 企画の概要

### 2.1 システム名

**AI-BIC（AI Business Improvement Consultant）**

### 2.2 一言でいうと

> 業務担当者にAIが「業務改善コンサルタントの初回ヒアリング」を行い、課題と改善案を**根拠つき**で整理するWebアプリ。

### 2.3 解決方法

| 課題 | AI-BICでの解決方法 |
|---|---|
| C1 言語化できない | 決められた診断項目（目的・作業内容・時間・ツール・問題点・制約）に沿ってAIが1問ずつ質問し、回答を構造化する |
| C2 ヒアリングの属人化 | 診断フレームワーク（7つの評価観点）を固定し、誰が使っても同じ観点で診断する |
| C3 事実と推測の混同 | 分析結果で「確認された事実」「推測」「要確認」を明示的に分けて表示する |
| C4 システム導入ありき | 改善案を「ルール見直し → 標準化 → 既存ツール活用 → 自動化 → 新規システム」の順で検討させる |

### 2.4 AIの使い方の特徴（ハイブリッド型ヒアリング）

AIに自由に質問させるチャットボットではなく、**あらかじめ決めた診断項目（骨組み）をプログラムが管理し、AIは「次にどの項目を、どう聞くか」と「曖昧な回答への確認」を担当する**方式とする。

| 方式 | 長所 | 短所 | 採否 |
|---|---|---|---|
| 固定アンケート型 | 結果が安定、AI費用ゼロ | 回答に応じた深掘りができない | 不採用 |
| 自由チャット型 | 柔軟 | 質問の漏れ・重複、品質が不安定、費用が読めない | 不採用 |
| **ハイブリッド型** | 漏れを防ぎつつ深掘りできる。回数上限で費用も管理しやすい | 設計がやや複雑 | **採用** |

## 3. 想定ユーザー

| # | ユーザー | 主な利用シーン |
|---|---|---|
| U1 | 情報システム部門担当者 | 現場からの改善相談の一次受付・事前整理 |
| U2 | DX推進担当者 | 部門ごとの業務課題の棚卸し |
| U3 | 業務改善担当者 | 改善テーマの洗い出し |
| U4 | ITコンサルタント | 顧客ヒアリング前の仮説づくり |
| U5 | 中小企業の管理職 | 自部署の業務の見直し（ITに詳しくない前提） |

**最も重視するユーザー：U5（ITに詳しくない管理職）**。この人が迷わず使えれば、他のユーザーも使える。

## 4. MVP（最小限の製品）の範囲

### 4.1 作るもの

| ID | 機能 | 概要 |
|---|---|---|
| F01 | 業務情報登録 | 部署・業務名・業務概要・困っていることを入力 |
| F02 | AI業務ヒアリング | 診断項目に沿ってAIが最大5回まで質問 |
| F03 | 業務課題分析 | 課題・原因・影響・重要度・根拠・要確認事項を出力 |
| F04 | 業務改善提案 | 最大3つの改善案を、難易度・リスク・推奨理由つきで出力 |
| — | デモモード | APIキーなしで、架空シナリオと固定結果で画面を確認できる |

### 4.2 作らないもの（今回の対象外）

- 費用対効果（ROI）分析、As-Is／To-Be業務フロー図、改善ロードマップ、要件定義書の自動生成
- 製造業・情報システム部門向けの専門診断モジュール
- ユーザー登録・ログイン、複数人での共有、診断結果の一覧管理
- PDF・Excelでの結果出力

対象外の機能は、**後から追加できる構成（診断項目や観点を設定ファイルで管理する等）**にしておく。

## 5. 期待される効果（想定値）

> 以下はすべて**想定値**であり、実測ではない。MVP完成後、架空シナリオで所要時間を測定して検証する。

| 観点 | 従来（想定） | AI-BIC利用時（目標） |
|---|---|---|
| 初回ヒアリングの所要時間 | 対面で30〜60分 | 利用者の入力で10〜15分 |
| 課題整理のばらつき | 担当者のスキルに依存 | 7観点で同じ基準 |
| 改善案の偏り | システム導入に偏りがち | ルール見直しから段階的に検討 |

## 6. 技術構成（候補）

| 項目 | 技術 | 選定理由 |
|---|---|---|
| 言語 | Python | 学習中の言語。AI・業務自動化で広く使われる |
| 画面 | Streamlit | Pythonだけで画面を作れる。前回の個人開発でも使用経験あり |
| AI | Claude API（Anthropic公式Python SDK） | 日本語の品質、構造化出力（JSON形式での回答）に対応 |
| データ保存 | SQLite | 1ファイルで動き、サーバー不要 |
| テスト | pytest | 指示書の指定。AI呼び出しを偽物に差し替えるテストが書きやすい |
| 公開 | Streamlit Community Cloud | 無料で公開でき、採用担当者がURLで確認できる |

詳細な選定理由と代替案の比較は、基本設計書で記載する。

## 7. コストの考え方

目標：**Claude APIの利用料を月額3,000円以内**。

| モデル | 入力（100万トークンあたり） | 出力（100万トークンあたり） |
|---|---|---|
| Claude Haiku 5.5（低価格） | $0.10 | $0.50 |
| Claude Sonnet 5.5（中価格・高品質） | $2.00 | $10.00 |

※ 2026年10月時点の公表価格（開発ツール内の情報）。実装時に公式サイトで再確認する。

1回の診断あたりの概算（**想定値**、1ドル=150円で計算）は要件定義書「8. コスト見積もり」を参照。いずれのモデルでも、ポートフォリオとしての利用規模（月数十回程度）であれば目標内に収まる見込み。

ただし、**アプリ内の制限だけでは予算上限を保証できない**（不具合や第三者による大量利用がありうる）。そのため、API提供元（Anthropic Console）側の**利用上限（Spend limit）設定を必須**とする。
