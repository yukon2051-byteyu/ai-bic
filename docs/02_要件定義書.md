## 1. 目的

企業の業務担当者にAIがヒアリングを行い、現状業務の問題点を分析し、改善施策を提案する。
MVPでは、業種を問わない汎用的な事務業務を対象とする。

## 2. 用語の定義

| 用語 | 意味 |
|---|---|
| 診断 | 業務情報の登録 → ヒアリング → 分析 → 改善提案までの一連の流れ（1セッション） |
| 診断項目 | ヒアリングで必ず確認する6つの情報（目的・作業内容・時間と頻度・使用ツール・問題点・制約条件） |
| 評価観点 | 課題分析で業務を評価する7つの切り口（業務効率・標準化・自動化可能性・データ管理・人的ミス・属人化・システム連携） |
| AI応答 | AIへのAPI呼び出し1回で返ってくる回答 |
| 構造化出力 | AIの回答を、決められた項目を持つJSON形式で受け取ること。プログラムで項目ごとに検証・表示できる |
| デモモード | AIを呼ばず、架空シナリオと固定の診断結果で画面を確認するモード |
| 要確認 | 根拠が不足し、事実として断定できない内容に付ける表示 |

## 3. 対象範囲

### 3.1 対象業務（MVP）

Excel集計、データ入力、報告書作成、申請・承認、情報共有、問い合わせ対応、手作業による転記などの汎用的な事務業務。

### 3.2 対象外

- 製造業向け・情報システム部門向けの専門診断モジュール（将来追加できる構成にする）
- 費用対効果分析、As-Is／To-Be業務フロー、ロードマップ、要件定義書の生成
- ユーザー認証、診断結果の共有・一覧管理、ファイル出力

## 4. 想定ユーザーと利用環境

| 項目 | 内容 |
|---|---|
| ユーザー | 情報システム部門担当者、DX推進担当者、業務改善担当者、ITコンサルタント、中小企業の管理職 |
| ITリテラシー | 最も低いユーザー（ITに詳しくない管理職）を基準にする |
| 利用端末 | PCのWebブラウザ（Chrome / Edge の最新版）。スマートフォンは表示崩れがない程度に対応 |
| 利用人数 | 同時利用は数人程度（ポートフォリオとしての公開を想定） |

## 5. 業務の流れ（利用シナリオ）

```
[トップ画面] ─ 注意事項を確認、通常／デモを選ぶ
     │
     ▼
[業務情報入力] ─ 部署・業務名・概要・困りごとを入力（F01）
     │
     ▼
[AIヒアリング] ─ AIが1問ずつ質問（最大5回）、利用者が回答（F02）
     │            途中で「診断を終了」も可
     ▼
[診断結果] ─ 課題分析（F03）と改善案（F04）を表示
```

### 6.2 F01：業務情報登録

| 入力項目 | 必須 | 文字数上限（案） | 備考 |
|---|---|---|---|
| 企業名 | 任意 | 50 | 架空名・空欄を推奨と表示 |
| 部署名 | 必須 | 50 | |
| 業務名 | 必須 | 50 | 例：月次売上集計 |
| 業務概要 | 必須 | 1,000 | |
| 現在困っていること | 必須 | 1,000 | |

- 必須項目が空欄（空白文字のみも含む）の場合、**どの項目が未入力かを項目ごとに**表示し、次へ進ませない
- 文字数上限を超えた場合、上限と現在の文字数を表示する
- 入力欄の近くに「個人情報・機密情報は入力しないでください」と表示する

### 6.3 F02：AI業務ヒアリング

#### 診断項目（ヒアリングで埋める6項目）

| # | 診断項目 | 確認したいこと（例） |
|---|---|---|
| H1 | 業務の目的 | 誰のため、何のための業務か。成果物は何か |
| H2 | 作業内容 | どんな手順で、何を入力し、何を出力するか |
| H3 | 作業時間・頻度 | 1回あたりの時間、頻度（毎日／月次等）、担当人数 |
| H4 | 使用ツール | Excel、メール、基幹システム、紙など |
| H5 | 業務上の問題点 | ミス、手戻り、待ち時間、特定の人しかできない等 |
| H6 | 改善に向けた制約条件 | 予算、使えるツールの制限、社内ルール、IT担当の有無 |

#### ヒアリングの仕様

| # | 仕様 | 実現方法（方針） |
|---|---|---|
| R1 | 一度に質問するのは原則1項目 | AIの出力形式を「質問1つ＋対象の診断項目」に固定する |
| R2 | 回答に応じて次の質問を決める | AIに、各診断項目の充足状況（充足／不十分／未確認）を判定させ、未充足の項目から次の質問を選ばせる |
| R3 | 回答済みの内容を繰り返し聞かない | F01の入力内容と過去の質問・回答をすべてAIに渡し、充足済み項目は質問対象外とする |
| R4 | 曖昧な回答には確認質問をする | 判定が「不十分」の項目には、具体化を促す確認質問を許可する |
| R5 | 最大5回のAI応答で終了 | 回数はプログラム側で数え、5回に達したら自動的に分析へ進む（AIの判断に任せない） |
| R6 | 情報不足の場合は不足項目を明示 | 終了時点で「未確認」「不十分」の診断項目を結果画面に一覧表示する |
| R7 | 途中で診断を終了できる | 「ここまでの情報で診断する」「診断を中止する」の2つを用意する（決定事項 Q5） |
| R8 | 自然な日本語の質問 | 業務改善コンサルタントの口調、専門用語を避ける、回答例を添える |
| R9 | 情報が十分ならば5回未満でも終了できる | 全診断項目が「充足」と判定されたら分析へ進む |

#### 診断フレームワーク（評価観点）

業務効率、業務標準化、自動化可能性、データ管理、人的ミス、属人化、システム連携の7観点。
**診断項目と評価観点は、プログラム本体ではなく設定ファイルで定義し**、追加・変更できるようにする。

### 6.4 F03：業務課題分析

各課題について次を出力する。

| 項目 | 内容 |
|---|---|
| 課題名 | 短い名称 |
| 課題の概要 | 何が問題か |
| 想定原因 | 推測であることを明示 |
| 業務への影響 | 時間・品質・リスクなど |
| 重要度 | 高／中／低（判定基準は基本設計で定義） |
| 関連する評価観点 | 7観点のどれか（複数可） |
| 判断根拠 | **ユーザーの回答のどの部分に基づくか**を引用・要約 |
| 根拠の種別 | 「事実（回答で確認済み）」「推測」「要確認」 |
| 追加確認事項 | 判断を確定するために聞くべきこと |

**重要な設計条件**

- 根拠が回答に存在しない内容を「事実」としない。根拠不足のものは「要確認」と表示する
- 問題が確認できない観点について、課題を作り出さない（課題が0件・1件でもよい）
- AIの出力をプログラムで検証する（必須項目の欠落、重要度の値が範囲外、根拠の種別が不正 → エラー扱い）

### 6.5 F04：業務改善提案

最大3件。各改善案に次を含める。

| 項目 | 内容 |
|---|---|
| 改善施策名 | |
| 改善の種類 | ①業務ルールの見直し ②業務標準化 ③既存ツールの活用 ④自動化 ⑤新規システム導入 |
| 改善内容 | 具体的に何をするか |
| 対応する課題 | F03のどの課題を解決するか |
| 期待できる効果 | 定量的な効果は「想定」と明記 |
| 導入難易度 | 高／中／低 |
| 想定リスク | |
| 実施前に確認すべき事項 | |
| 推奨理由 | なぜこの案か、他の種類より優先する理由 |

**設計条件**

- 改善案は①→⑤の順に検討させ、⑤新規システム導入を提案する場合は「①〜④では解決できない理由」を必須とする
- 改善案が課題と対応していない場合（対応する課題が空）はエラー扱いとする

### 6.6 F05：デモモード

- 架空の業務シナリオ（最低1件、AI品質評価用と共用して3件を想定）を選んで実行する
- 質問・回答・診断結果はすべて事前に用意した固定データを使う
- **全画面の上部に「デモモード：AIは使用していません（固定の結果です）」と常に表示する**
- APIキーが未設定でも動作する

### 6.7 F06：利用状況の記録

| 記録する | 記録しない |
|---|---|
| 日時、呼び出し種別（ヒアリング／分析／提案）、使用モデル、入力・出力トークン数、成否、エラー種別 | 入力された業務内容、回答本文、AIの回答本文、APIキー |

## 9. コスト見積もり（想定値）

### 9.1 前提（すべて仮定）

| 前提 | 値 |
|---|---|
| 為替 | 1ドル = 150円 |
| 1診断あたりのAI呼び出し | 最大7回（ヒアリング5回＋分析1回＋提案1回） |
| 1診断あたりの入力トークン | 約25,000（会話履歴を毎回送るため、回を追うごとに増える） |
| 1診断あたりの出力トークン | 約8,000（AIの内部的な思考分を含めた概算） |

### 9.2 1診断あたりの費用

| モデル | 入力 | 出力 | 合計 | 3,000円で可能な診断回数（目安） |
|---|---|---|---|---|
| Claude Haiku 5.5 | 約0.4円 | 約0.6円 | **約1円** | 約3,000回 |
| Claude Sonnet 5.5 | 約7.5円 | 約12円 | **約20円** | 約150回 |

計算例（Sonnet 5.5）：入力 25,000 ÷ 1,000,000 × $2.00 = $0.05、出力 8,000 ÷ 1,000,000 × $10.00 = $0.08、合計 $0.13 ≒ 20円

> 実際のトークン数は実装後に F06 の記録で**実測**し、テスト結果に記載する。開発中のテスト実行・AI品質評価でもAPI料金が発生する点に注意。

### 9.3 予算を守るための多重の対策

| 層 | 対策 | 効果 |
|---|---|---|
| 1. API提供元 | Anthropic Console の利用上限（Spend limit）・通知、プリペイド残高の範囲で利用 | **唯一の確実な上限**。アプリの不具合があっても超えない |
| 2. アプリ（全体） | 1日あたりの診断回数上限 | 第三者による大量利用の抑制 |
| 3. アプリ（診断ごと） | 呼び出し回数上限・入力文字数上限・`max_tokens` | 1診断の費用の上限を固定 |
| 4. 記録 | F06の利用状況記録 | 実際の利用量の把握と見直し |

**アプリ内の制限だけでは予算の上限を保証できない**（Streamlit Community Cloudはアプリの再起動でデータが消えることがあり、回数の記録がリセットされる可能性があるため）。そのため、層1の設定を必須とする。

## 10. 決定事項・設計上の論点

### 10.1 開発者が決定した事項（2026-11-01）

| ID | 論点 | 決定内容 | 理由 |
|---|---|---|---|
| Q1 | 既存の README.md の扱い | 削除してAI-BIC用に新規作成 | 既存の README.md は別プロジェクト（社内IT資産管理システム）の内容で、残すと採用担当者が混乱する |
| Q2 | 使用するAIモデル | ヒアリング＝Claude Haiku 5.5、分析・提案＝Claude Sonnet 5.5（設定で切替可能） | 質問生成は軽い処理なので低価格モデルで十分。分析・提案は成果物の価値を決めるため上位モデル。AI品質評価で最終確認する |
| Q3 | 公開環境での利用制限 | AI診断にアクセス用パスワードを設定。デモモードはパスワード不要 | 採用担当者に実際のAI診断を見せられ、かつ第三者の大量利用による課金を抑えられる |
| Q4 | 1日あたりの診断回数上限 | 20回 | Sonnet併用でも1日最大約400円（想定値）。超過しそうな場合は提供元の利用上限で止まる |
| Q5 | 途中終了時の動作 | 「ここまでの情報で診断する」「診断を中止する」の両方を用意 | 「急いでいるが結果は見たい」と「やめたい」は別のニーズ。前者は不足項目を明示する |
| Q6 | 診断結果の保存 | 保存しない。SQLiteには利用状況（F06）のみ記録 | 機密情報が残らない。Streamlit Community Cloudではファイルが消える可能性があり、保存の価値が低い |
