## 1. 開発の進め方

要件定義 → 基本設計 → 詳細設計 → 実装 → テスト → AI品質評価の順に進め、各工程の終わりに開発者がレビューして承認した。工程ごとの成果物は docs/ に残し、変更は版数と変更履歴で管理した（要件定義書は0.4版、詳細設計書は0.10版まで更新）。

実装しながら設計の見落としに気づいたときは、コードだけを直さず、設計書にも「※実装時の追記」として理由とともに反映した。

### 2.1 面接で具体的に説明する判断（外部評価 X02・1.1で追加）

外部評価で「公開物だけでは本人の理解度が分からない」と指摘されたため、本人が判断・発見したことを5つに絞って書く。項目は開発者が選んだ。「理由」は記録をもとにAIが下書きしたもので、面接では自分の言葉で話す。

**本人が決めた要件（3点）**

| 要件 | 何を決めたか | 理由 | AIの役割 |
|---|---|---|---|
| 資料の添付機能（F09） | ヒアリングだけでなく、集計表や記録（CSV・テキスト・Excel）を診断の根拠に使える機能を**発案**し、対応形式・上限（3ファイル・合計1万文字）・使う場面（ヒアリングの後、課題分析だけ）を決めた | 業務改善の現場では、担当者の話だけでなく実際の記録を見て判断する。話と記録が食い違う場面も確かめたい。上限は費用を抑えるため。超えたときに黙って切り捨てず、エラーにした | 仕様の選択肢と費用の見積もりの提示、実装、テスト |
| 採用担当者向けの公開方法（Q3） | AI診断はパスワード制にして職務経歴書で伝え、デモはパスワードなしで誰でも試せるようにした | 採用担当者には本物のAIの診断を見てほしい。一方で、URLを知った第三者に使われて料金が発生するのは防ぎたい。この2つを両立させるため | パスワードの照合と回数制限の実装 |
| 診断結果を保存しない（Q6） | 入力された業務の情報と診断結果はサーバーに保存せず、利用状況（日時・回数・トークン数）だけを記録する | 業務の情報や社外秘の内容が残らないようにする。結果は利用者が Excel のレポートで手元に残せる | 「本文を受け取る引数そのものがない」記録の関数の設計と実装 |

**採用しなかった案（1点）**

| 案 | 判断 | 理由 |
|---|---|---|
| 外部のデータベースを追加する（外部評価 X01） | 採用しなかった。AIが示した対策案の中から、外部のデータベースを使わない案を選んだ | 公開環境（Streamlit Community Cloud）は再起動でファイルが消え、1日の回数の記録も0に戻る。外部のデータベースを使えば記録は残るが、設定・費用・保守が増える。費用の確実な上限は API提供元の前払い残高と利用上限で確保できているので、アプリの中の制限は「同時に使われても超えない」ところまでにとどめ、再起動で記録が戻るという限界を README に明記した |

**自分で見つけた不具合と改善（1点）**

| できごと | 内容 |
|---|---|
| 発見 | 外部評価の指摘 B01 の修正を公開した直後、公開版で自分でデモを操作し、結果画面で AttributeError が出ることを見つけた（画面の画像で報告） |
| 原因（AIが分析） | 手元の自動テストはすべて合格していた。公開環境は、push するとサーバーを止めずにプログラムだけを差し替えるため、新しいプログラムと古いデータが混ざって動いていた |
| 対応と改善 | アプリを再起動して解消したことを、自分で確認した。そのうえで「データの形を変える更新を公開した後は、アプリを再起動してから確認する」という運用の手順にして、テスト結果に記録した |
| 学び | 手元のテストに合格しても、公開した環境で実際に操作して確かめるまでは完了ではない |

### 2.2 AI-BIC 2.0 での開発者の判断と指摘（1.2で追加・2026-11-04〜11-09）

AI-BIC 2.0 の指示書（3機能の追加）は開発者が用意した。実装はAIが行い、開発者は判断・承認・画面での確認と指摘を行った。

| 種類 | 開発者が判断・指摘したこと | その結果 |
|---|---|---|
| 運用の課題の発見 | 公開先（Streamlit Community Cloud）が休止し、採用担当者が見られないタイミングがあることに気づいた | 休止条件を比べて Hugging Face Spaces に移行（06 4.1） |
| 公開URL の指摘 | 「他のアプリは枠のない直リンクなのに、なぜ枠つきのURLなのか」 | アプリ本体のURL（.hf.space）に変更 |
| 設計の判断（4点） | 効果試算を作業中だった B06 の土台の上に作る／業務フローは今の診断のあとに追加する（改善案の作り方は変えない）／図は Graphviz／AIの回数の上限（フロー1・レビュー3・作り直し2） | Phase 0 で選択肢から選んだ |
| デモへの指摘 | 「デモの試算が空欄ではデモの意味がない」 | 3つのデモにデモ値を入れた。以後「新機能はデモで見られる状態にしてから報告する」ことにした |
| 画面への指摘（4点） | 「1920×1280でも、どの案がどれだけ減り何か月で回収できるかを1画面で」「『デモ値』で1行取るのはもったいない」／TOP画面を20〜25%詰める／最上部の余白は3分の1に／デモを始めるまで1画面に（横幅を広げてよい） | 比較表を最上部へ、出どころを1行に、余白と並べ方で詰めた |
| 追加の要件（3点） | ヒアリングを情報の充足度に応じた追加確認（最大3問、任意）にする／業務フロー図をコンパクトにし、ズーム・パン・選択で詳細／どの画面でもブランド名でTOPに戻る | 要件どおり実装。追加確認の判定基準（機能↔必須の項目の対応表）は開発者が承認した |
| 費用の判断 | 本物のAIでの確認を、内容と費用の見込みを聞いたうえで承認した（計約137円） | 自動テストでは見つからない問題を3つ見つけて直した（06 3.13） |

**AIが判断したこと（開発者が承認または事後に確認）**：読み込んだAI診断の案件ではAIを使わない（費用の上限を守るため）、製造業デモをデモの初期表示にする、01カードの文言を「追加します」から「追加できます」に変える（実装に合わせるため）、TOPへのリンクでは入力中の内容が消えることをマウスを乗せたときに示す。

## 3. 技術面で学んだこと

### 3.1 生成AIの出力は「信じる」のではなく「確かめる」

AIは、ルールをお願いしても「たいてい守る」が「必ず守る」とは限らない。本開発では、AIに任せる部分とプログラムで確実に守る部分を分けた。

| 守りたいこと | ルールで頼む（プロンプト） | 仕組みで守る（プログラム） |
|---|---|---|
| 決まった形で回答させる | 「JSONで答えて」 | 構造化出力＋Pydantic で形式を保証 |
| 事実と推測を分ける | 「根拠のある事実だけを書いて」 | 引用が入力に実在するかを照合し、なければ「要確認」に格下げ |
| 質問は5回まで | （AIには任せない） | 回数はプログラムが数える |
| 同じ項目を聞き続けない | 「同じ項目は2回まで」 | 項目ごとの回数をプログラムが数えてAIに渡し、3回目はチェックで拒否 |
| 新規システムを安易に勧めない | 「簡単な方法から検討して」 | 新規システム導入には「より簡単な方法では不十分な理由」を必須に |

**学び：** プロンプトだけでも、プログラムのチェックだけでも不十分な場面があった。チェックだけでは「AIがルールを知らずに同じ間違いを繰り返し、エラーで止まる」副作用が起きた（06 3.2の③）。**AIが間違えにくい情報を渡し、それでも間違えたらプログラムが止める**という二重の対策が有効だった。

### 3.2 テストでは本物のAIを使わない

本物のAIを使うと、料金がかかり、回答が毎回変わってテストの結果が安定しない。AIの呼び出し部分を「本物・デモ・テスト用の偽物」で差し替えられる設計にしたことで、272件（2026-11-01時点。最新の件数は[テスト結果の「0. 最新の検証結果」](06_テスト結果.md#0-最新の検証結果)）のテストを料金ゼロ・約18秒で何度でも実行できた。通信エラーや利用制限のように、本物では狙って起こせない異常系も、偽物にわざとエラーを出させて確認できた。

### 3.3 テストが「誤りを見つけられるか」も確かめる

テストが成功しても、テストそのものが甘ければ意味がない。重要な仕組み（二重呼び出しの防止、攻撃対策、添付ファイルの照合）では、**わざと不具合を入れてテストが失敗すること**を確かめた。

### 3.4 費用は「想定」と「実測」を分けて管理する

要件定義では1回の診断を約24円と見積もったが、実測は約30円だった。差の理由（改善案の項目を増やして出力が増えた）を記録した。また、アプリ内の制限（1日20回）だけでは不具合やキーの流出時に料金を止められないため、**API提供元の前払い残高（自動チャージなし）を確実な上限**とした。

### 3.5 セキュリティは「入力が何であっても安全」に

| 対策 | 内容 |
|---|---|
| APIキー | ソースコードに書かず、Secrets で管理。コミットのたびにキーの形式で検索して確認 |
| プロンプトインジェクション | 利用者の入力をタグで囲み、入力中の `<` `>` を全角にして、囲みから抜け出せないようにした |
| XSS | AIの回答や入力をHTMLで表示するとき、すべてエスケープした |
| 個人情報 | 業務内容は保存しない。利用状況の記録には本文の列そのものを作らず、「誤って記録することもできない」作りにした |

## 4. 業務改善の観点で学んだこと

- **ヒアリングは「骨組み」と「深掘り」を分ける：** 確認すべき6項目（目的・作業内容・時間・ツール・問題点・制約）を骨組みとして固定し、AIには深掘りの質問だけを任せた。これにより、聞き漏れと的外れな質問を減らせた
- **判断の基準は言葉にしておく：** 「充足」の条件や重要度の基準を明文化したことで、AIの判断のぶれが減った。逆に、条件の表現があいまいだと、AIが不要な再質問をした（06 3.2の②）。人のヒアリングでも、基準の言語化は品質に直結する
- **制約条件を聞けるかどうかで、診断の質が大きく変わる：** 最初の評価で制約条件（H6）を聞きそびれたときは、「集計方法を知っているのは私だけ」という最重要の課題を見落とした
- **改善案は「最初の一歩」まで落とす：** 一般論の改善案は物足りないという感想を受け、「今週から始められる行動」と「導入前後の比較」を加えた。提案の説得力は、具体性と実行のしやすさで決まる
- **システム導入ありきにしない：** ルールの見直し → 標準化 → 既存ツール → 自動化 → 新規システムの順で検討させた。評価した3シナリオでは、新規システムの提案は0件だった

## 5. うまくいかなかったことと、その対応

| できごと | 対応 |
|---|---|
| AIが「分かりません」と答えた項目を3回連続で質問した | プロンプトとプログラムの二重の対策（06 3.2の①） |
| プログラムのチェックだけでは、エラーで止まる副作用が出た | プログラムが数えた結果をAIに渡す方式に変更（06 3.2の③） |
| デザインの変更で、アイコンが文字（visibility など）で表示された | 書体の指定の範囲を絞り、再発防止のテストを追加 |
| 画面の見た目を自動で確認できなかった | 開発者が目視で確認し、画面の画像で指摘する運用にした |
| 1回の診断の費用が見積もりより約25%高かった | 理由を分析して記録。前払い残高で上限を確保 |
| 2.0：AIの業務フローが「1件」を月の作業全体と解釈し、初回の作業も毎回の時間に入れた（本物のAIで発見） | 「1件」の意味と月の件数を出させて照合し、初回の作業は別に出させた。再確認で解消 |
| 2.0：レビューのAIに渡す資料に実施割合がなく、AIが合計時間を誤った（本物のAIで発見） | 資料に実施割合と合計を入れた。再確認で解消。**渡す情報が足りないと、AIは正しく推論できない** |
| 2.0：業務フロー図で文字がはみ出し、図が崩れた（実際に描いて発見） | 画像にして目で見て、3つの原因を直した。自動テストは「描けること」しか確かめられない |
| 2.0：デモの試算を空欄のまま報告した（開発者の指摘） | 新機能はデモで見られる状態にしてから報告するよう改めた |

## 6. 面接での説明の例（下書き）

> ※AIが作成した下書きです。実際に話すときは、ご自身の経験や言葉に置き換えてください。

**1分の概要説明**
> 業務担当者にAIがヒアリングし、業務の課題と改善案を整理するWebアプリを、要件定義から設計・実装・テストまで一通り進めて作りました。工夫したのは、AIの出力をそのまま信じない仕組みです。たとえば、AIが「事実」とした課題は、根拠として挙げた発言が利用者の入力に本当にあるかをプログラムで照合し、確認できなければ「要確認」に格下げします。また、本物のAIで評価したところ、同じ質問を繰り返す問題が見つかったので、原因を分析して対策し、再度測って解消を確認しました。

**品質管理について聞かれたら（状況 → 課題 → 行動 → 結果）**
> - **状況：** 本物のAIで3つの架空の業務シナリオを評価しました
> - **課題：** 質問を作るAIが同じ項目を聞き続け、5問中3問を無駄にしたり、途中でエラーになったりしました
> - **行動：** プロンプトでのお願いだけでは守られないと考え、項目ごとの質問回数をプログラムが数えてAIに渡し、それでも違反した場合はプログラムが止める二重の仕組みにしました
> - **結果：** 3シナリオすべてが最後まで完了し、制約条件まで聞けるようになったことで、見落としていた最重要の課題も抽出できるようになりました

**費用管理について聞かれたら**
> 月3,000円以内を目標に、モデルの使い分け（質問は安くて速いモデル、分析は高性能なモデル）、回数の上限、二重呼び出しの防止を入れました。ただ、アプリ内の制限だけでは不具合時に止められないので、API提供元の前払い残高を確実な上限にしています。1回の費用は見積もり24円に対して実測30円で、差の理由も記録しています。

## 7. 今後の課題

- 改善の余地（06 3.4）の対応：述べていない役職を使う、入力済みの内容を質問する、「分かりません」を根拠に引用する
- 公開環境（Streamlit Community Cloud）での動作確認
- 専門診断モジュール（製造業向け・情報システム部門向け）の追加：診断フレームワークの設定ファイルを追加する形で拡張できる
- 改善ロードマップの生成（費用対効果の試算と As-Is／To-Be 業務フローは AI-BIC 2.0 で実装済み）
- 業務フロー図の表示部品（st.components.v1.html）は、Streamlit で削除予定とされている。Streamlit を上げる前に書き換える
- AIが回答を拒否したときに別のモデルでやり直す設定（fallbacks）の検討
